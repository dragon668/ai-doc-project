# AI 文档协作工作台

> 当前状态说明：这是一个已完成工程骨架和核心主流程的全栈项目，具备可演示、可联调、可继续迭代的基础。项目当前已经覆盖用户认证、工作区、文档管理、版本控制、AI 对话、文档分享和基础大文件上传流程，但仍有若干生产化能力和高级 AI 能力尚未完全落地。

---

## 1. 项目概述

本项目是一个“Java 后端 + Vue 前端 + Python AI 服务”的私有化文档协作平台，目标是将文档管理、团队协作、知识库问答和 AI 生成改写能力组合到同一套系统中，适合内部知识沉淀和团队工作流管理。

当前版本的重点不是“追求完美的企业产品”，而是先把最关键的落地能力打通：

- 用户/团队/空间权限管理
- 文档上传、版本、回滚
- AI 对话与知识库问答
- 文件分享与只读访问
- 大文件分片上传和 MinIO 存储
- 后端 + 前端 + AI 服务之间的联调

## 2. 当前已完成内容

### 2.1 基础系统与工程骨架

已完成：

- Java 后端采用 Spring Boot 3.2.5
- 项目已使用 Java 21 编译目标
- MyBatis-Plus 作为 ORM 框架
- Spring Security + JWT 组合完成权限控制与登录态校验
- Vue 3 + Vite 前端工程已搭建，并加入路由和鉴权守卫
- Python AI 服务已拆成独立模块，便于后续扩展 RAG 能力
- Docker / Compose 结构已具备基础部署能力

实现方式：

- 后端以 Spring Boot 启动，统一处理 REST API、权限和业务逻辑
- 前端通过 Vue Router + Pinia 管理页面访问和状态
- AI 服务单独部署，后端通过 HTTP 调用接入大模型能力
- 中间件由 MySQL、Redis、MinIO、RocketMQ、XXL-Job 组合支撑

### 2.2 用户、工作区与权限

已完成：

- 注册、登录、退出
- 创建/进入工作区
- 当前用户与 workspace 的绑定
- 基本团队成员与空间访问模型
- 分享链接只读访问机制

实现方式：

- JWT 负责用户认证
- Security 拦截关键接口
- 服务层再做权限校验，防止前端绕过访问限制
- 共享链接通过 token + 过期时间 + 访问密码进行限制

### 2.3 文档管理

已完成：

- 文件/文件夹结构管理
- 文档元数据保存
- 文档内容新增、保存、读取
- 文档删除
- 版本保存与回滚
- 基础的文档列表与详情展示

实现方式：

- MinIO 保存文件对象
- MySQL 保存文档及版本信息
- 每次更新文档内容时可保留历史版本
- 回滚时切换到指定版本对应文件

### 2.4 大文件上传

已完成：

- 秒传检测
- 分片上传
- 分片合并
- 文件 MD5 校验
- 传输过程的断点续传基础逻辑

实现方式：

- 前端计算文件 MD5
- 后端初始化上传，检查 Redis/数据库中是否已有相同文件
- 大文件按块上传到 MinIO 或临时存储目录
- 合并时生成最终文档对象并写入数据库
- 上传结果与文档状态联动

### 2.5 AI 对话和文档生成

已完成：

- AI 会话创建与消息记录
- SSE 流式返回聊天结果
- 文档生成入口
- AI 改写入口与后端调用链

实现方式：

- 前端发起 AI 请求
- 后端接收问题/指令后转发到 Python AI 服务
- AI 服务调用大模型，并以流式返回的方式返回内容
- Java 后端处理消息结果并落库保存生成/改写后的文档

### 2.6 统计看板与基础运维信息

已完成：

- 工作区总览页面
- 文件数量、存储量等基础结构化展示
- 统计页基础布局与数据展示

实现方式：

- 后端聚合业务数据
- 前端渲染统计卡片和图表
- 为后续审计和运营分析留出接口与页面入口

## 5. 实现方式与设计思路

### 5.1 架构分层

当前实现采用“前端 + 后端 + AI 服务 + 中间件”四层结构：

- 前端负责交互与页面展示
- Java 后端负责业务逻辑、权限校验、数据库和对象存储交互
- Python AI 服务负责大模型调用、文本抽取和 RAG 流程
- MySQL / Redis / MinIO / MQ / XXL-Job 负责数据、缓存、异步任务和存储能力

### 5.2 关键设计原则

1. 业务与 AI 能力解耦
   - 业务逻辑放在 Java 后端
   - AI 能力放在独立 Python 服务中
   - 两者通过 HTTP 接口通信

2. 文件存储与数据库分离
   - 文件对象保存在 MinIO
   - 文档信息保存在数据库
   - 这样的结构有利于扩展和降低数据库压力

3. 权限在后端二次校验
   - 前端只负责展示与交互
   - 所有关键操作最终以后端权限验证为准

4. 异步能力作为生产能力补齐手段
   - 解析、向量化、清理任务采用异步方式
   - 这是处理大规模文档和低延迟体验的关键思路

## 7. 当前可运行方式

### 7.1 本地开发启动

1. 启动基础中间件：

```bash
docker-compose up -d mysql redis minio rocketmq-namesrv rocketmq-broker
```

2. 启动后端：

```bash
cd backend
./mvnw clean package
java -jar target/*.jar

cd C:\Users\21021\Desktop\creat\ai_wendang\backend
.\mvnw.cmd clean package
java -jar target\ai-doc-workspace-1.0.0.jar
```

3. 启动 AI 服务：

```bash
cd ai-service
pip install -r requirements.txt
# PowerShell
$env:OPENAI_API_KEY = "your-api-key"
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

4. 启动前端：

```bash
cd frontend
npm install
npm run dev
```

访问地址示例：

- 前端： http://localhost:5173
- 后端： http://localhost:8080
- AI 服务（本地开发调试）： http://localhost:8000/docs

说明：浏览器不直接调用 AI 服务。开发环境中前端请求先到 Vite，再由 Java 后端转发到本机 `8000`；Compose 部署时 AI 服务仅在 Docker 内网提供给后端访问，不发布 `8000` 到宿主机。

AI 接口配置在网页保存后由后端使用 AES-GCM 加密存储，列表接口只返回脱敏 Key。聊天消息也由后端加密保存，浏览器只接收当前会话所需内容。

### 7.2 运行现状判断

从当前代码与工程结构看，项目已经具备：

- 典型全栈应用的基础能力
- 业务主流程的联调能力

但仍属于“可演示、可继续迭代”的中期项目状态，而不是“全生产就绪”版本。
